# fix-sensenova-429-quota-retry

## Why

2026-09-04 的实测与事故复盘证明：SenseNova 渠道的 429 是**按分钟级配额桶限流**，而插件把它当作「秒级瞬时超限」处理——退避上限 3 秒、最多重试 1000 次且不轮换、不冷却。结果是多会话并发时形成重试风暴活锁：DSH 会话实录中连续 210 次 429 重试约 11.5 分钟仅 1 次成功，全程 266 次重试无一跨过配额窗口，用户只能手动中止（表现为「卡死」「无限重试」）。同时实测发现约 1/5 的请求会 ≥45 秒无响应挂起，而生成请求没有超时与看门狗，挂起期间并发闸额度被长期占用，是「卡死」的第二根源。

实测配额形态（2026-09-04，`token.sensenova.cn/v1`，两个 key 独立验证）：

- **速率配额（code 8，`quota_exceeded_error`，"rps/rpm exhausted"）**：per-key 令牌桶，容量 ≈5–6 个请求、补充 ≈1 个/14 秒（持续约 4–5 请求/分钟）。12 并发仅 5 个放行；1 req/s 连发 100 次仅 8 次成功，成功点严格每 ~14 秒一次。两个 key 各自独立限流（互不影响）。
- **TPM 配额（code 429001，"inference tpm exhausted"）**：事故现场（09-02 会话原始报错体）证实存在；本日实测 flash 档 44.5 万 input tokens/3min、pro 档 19.5 万 tokens/24s 均未触顶，说明档位高但多会话大上下文持续重试可触发。
- **429 响应不带 `Retry-After`、不带任何 `x-ratelimit-*` 头**：退避只能由客户端按桶模型自行计算，3 秒上限与 14 秒补充速率严重错配。
- **传输挂起**：当日 4 轮实测中约 1/5 请求 ≥45 秒无响应（无 RST、无响应体），生成请求无超时导致额度被占。
- **官方错误码表佐证**：SenseNova 官方将 429 归为 `quota_exceeded_error`（速率/额度超限，建议指数退避重试）、404 归为 `not_found_error`（模型不存在或已下线）。注意官方表的 `type` 与实测不一致：`429001 tpm exhausted` 实测返回 `invalid_request_error`，因此分类必须依据 `error.code` 而非 `type`。

## What Changes

- **429 按错误体分类**：解析 429 响应体的 `error.code`，区分「配额类」（code 8 速率耗尽、code 429001 TPM 耗尽）与其他 429；配额类给出与配额窗口匹配的退避指导（速率类 ≥15 秒量级、TPM 类 ≥60 秒量级），替换现行「一律 ≤3 秒短退避」。
- **重试预算收敛**：`providerRetryPolicy` 从 `maxRetries: 1000`、退避上限 3000ms 收敛为有限次数与可配置的长退避上限，使持续限流时失败尽早可见，而不是 1000 次 × 3 秒的无限观感。
- **生成请求超时与看门狗**：为生成请求增加连接/首字节超时与流空闲看门狗；并发闸排队等待增加超时，超时后交宿主重试层处理，消除「挂起占额度→后续永久排队」的卡死路径。
- **可选「配额类 429 粘性换 key」（新增设置，默认关闭）**：新增 `quotaRotation` 设置项（默认 `false`，位于高级设置折叠区）。开启后仅配额类 429 触发切换到下一把可用 key 并粘住新 key（环回后退回退避等待）；关闭时维持现行「429 不轮换」语义。429 永不冷却、永不禁用账号的规则不变。实测依据：配额桶与 TPM 池均 per-key 隔离（换 key 立即获得新桶）；「per-key prompt 缓存」实测价值很低（同 key 复用仅快约 13%、usage 无 `cached_tokens` 字段），一次切换的冷启代价远小于它避免的 15–60 秒配额等待。
- **BREAKING**：无（对外 API 与配置结构不变；仅错误语义、退避与超时行为变化）。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `sensenova-provider`：修改两条既有需求并新增一条需求——
  1. 「429 不冷却不轮换」（修改）：429 处理从单一语义改为按 `error.code` 分类；配额类 429（code 8 / 429001）SHALL 携带与配额窗口匹配的 `providerRetryAfterMs`（或等效退避指导）；默认不轮换，新增「配额类 429 换 key」可选开关（默认关闭，开启后粘性轮换）。
  2. 「Provider 重试策略」（修改）：`maxRetries` 与本地退避上限从 1000 次 / 3000ms 收敛为有限预算与更长的配额感知上限；`Retry-After` 透传规则随分类语义同步调整。
  3. 「生成请求超时与看门狗」（新增）：生成请求连接/首字节超时、流空闲看门狗与并发闸排队超时的要求，超时错误 SHALL 以可重试错误码交宿主重试层并释放并发额度。

## Impact

- **代码**：`src/adapter.ts`（429 错误体解析与分类、`providerRetryPolicy`、fetch/读取超时、配额类粘性轮换）、`src/concurrency.ts`（排队超时）、`src/index.ts`（`quotaRotation` 设置项与 schema）、`src/client/settings.ts`（高级区开关）；对应单元测试更新。
- **既有决策的影响**：与「429 = 常态性 RPM 瞬时超限」的旧前提冲突（该前提已被实测推翻：真实形态是分钟级配额桶）。设置页轮换文案无需变更（默认轮换语义不变）。
- **验证**：可复现路径为 `debug_quota_probe*.mjs` 实测脚本（突发/固定速率压测、传输挂起观察）与 DSH 双会话并发冒烟：修复后连续重试区间内应出现配额感知退避，且无「>10 次连续 3 秒短退避零成功」现象。
